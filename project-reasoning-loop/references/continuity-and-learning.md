# Continuity and current experience

Use this reference when a long task is interrupted by new messages or when old experience competes with a newer correction.

## Preserve the active outcome

Classify a new message by its relationship to the active outcome:

- **Question or status request:** answer it, then resume the unfinished authorized work.
- **Correction or critique:** replace the affected premise, step, or output and continue from the nearest valid checkpoint.
- **Additional requirement:** merge it when compatible; expose a real conflict when it changes scope or acceptance.
- **Local pause:** stop only the named branch, input, or method. Continue independent in-scope work.
- **Whole-task pause, cancellation, or replacement:** stop or switch as explicitly requested.

Do not infer cancellation from recency alone. Do not ignore an explicit correction merely to preserve momentum.

Before ending or resuming after compaction, recover:

1. the active outcome;
2. the latest effective correction;
3. accepted results that must be preserved;
4. unfinished work;
5. the exact blocker, if any;
6. the next safe falsifiable checkpoint.

A completed command, phase, draft, or status explanation is not the requested outcome unless the acceptance contract says it is.

Progress belongs in an interim update. After saying work is continuing, perform the next in-scope action in the same turn, or deliver the requested artifact. If a tool is still running, resume its existing wait and verify its result; do not restart it merely because a new message arrived. Do not promise future automatic continuation without an actual wake-up mechanism. A bounded execution agent may stop at its contract boundary while the owning task continues the remaining authorized outcome.

## Retrieve current applicable experience

Use the project's existing decisions, lessons, component registry, receipts, and evidence pointers. Search by current goal, object, version, failure class, and invalidation signal. Prefer:

1. current explicit instruction and direct evidence;
2. accepted current workflow and latest correction;
3. validated local lessons with matching scope;
4. counterexamples and failed routes that can still change the next action;
5. older narrative only when needed to resolve a contradiction.

Do not load every historical mistake by default. Do not hide a still-relevant counterexample merely because it is old. Keep retrieval output non-authoritative until reconciled with current sources.

## Find and adopt an applicable method

Use this procedure when the method owner is unknown, during relevant recovery, or after a correction exposes a route-selection failure. Reuse an already verified entrypoint when its inputs and authority have not changed; do not rediscover it every turn.

1. Identify the actual input object, requested operation and desired result. Use file type, application identity, explicit project reference and current scope as evidence; the current working directory or a generic word such as "loading" is not sufficient by itself.
2. Search the existing project contracts, method indexes, Skills and relevant local evidence. Prefer a current accepted route whose scope, prerequisites, invalidation conditions and evidence match the task. A search result is navigation, not a grant of authority or proof of maturity.
3. If there is no match, continue with applicable Skills or targeted local discovery. Distinguish "not found in this index" from "no experience exists". Do not manufacture a new project or run a returned reader just to demonstrate discovery.
4. Before invocation, inspect the real entrypoint's effects and current target. An API, launcher or background helper may still start an application, move focus, type, upload or mutate data. Follow the user's actual interaction and data boundaries; a Skill's historical permission statement or a failed background step cannot grant new authority.
5. Preserve working capabilities and accepted results. Diagnose only the failed step and affected relationships. Retain a genuinely authorized alternative instead of imposing a universal tool ban.

For a material failure, distinguish: discovery not triggered, no registered match, wrong match, method read but not used, invocation failed, or an authorized exception. Link the selected source and observed effect in the existing task or receipt; do not create a parallel tracking system.

Keep these claims separate: **rule written -> entry linked -> rule read -> method selected -> actually invoked -> requested effect observed**. Evidence at one stage does not establish the next. Updating a file does not prove an already-running task reloaded it. Frozen examples and fresh-process queries test their own layer, not natural model behavior or business success.

## Run the learning cycle

Use one auditable cycle:

```text
explore a possibility
-> test the highest-impact uncertainty
-> admit only decision-relevant evidence
-> retrieve it when a matching goal or failure appears
-> reuse within its scope
-> revise or retire it when negative feedback invalidates the relation
```

Small frozen cases can test whether a rule produces the intended structured judgment. They do not prove natural-task behavior, cross-model improvement, or reduced rework. Require comparable real-task evidence before making those claims.


## Deliver messages at the right time

Send corrections, authority changes, and execution-blocking instructions promptly. Keep non-urgent summaries in the existing project record until an agreed handoff or useful idle checkpoint; do not assume that a "no reply needed" message is a silent queue. Do not add a scheduler or message system merely to send ordinary updates.

Before sending or acting on an old request, reconcile the same source request, target and desired result with its latest reply, closure, withdrawal, replacement and dispatch receipt. Completed or withdrawn work is not reopened by an old annotation, compressed summary or late forwarded message. Reopen only for new evidence, a material scope change or an explicit human request; state the delta.

On receipt, inspect the relevant original span through its latest applicable correction. Forwarding is not fresh human authority. If delivery or execution is unknown, inspect the original call and authoritative state before retrying. A duplicate closed request needs no repeated work or acknowledgement. A local withdrawal stops only that matter, not the current independent objective.
