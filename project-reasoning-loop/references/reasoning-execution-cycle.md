# Reasoning-to-execution cycle

Use this protocol to preserve creative depth during exploration and execution reliability after a decision. It is a translation boundary, not another source of truth.

## Keep the axes independent

Track these dimensions separately:

- **Cognitive phase:** `Explore | Crystallize | Execute | Reflect`.
- **Governance mode:** `Light | Standard | Full`.
- **Knowledge type:** cognitive kernel, thinking operator, procedure or Skill, project truth, raw history or evidence.
- **Evidence maturity:** seed, candidate, project-validated, cross-project eligible, approved, retired.

Do not infer maturity from type. A compelling thinking operator may still be a seed; a verified project fact is not automatically a cross-project rule; raw history remains evidence rather than a Skill.

## Explore without inheriting the old answer

Load context in three classes:

- **Hard inherit:** current question, verified facts, explicit user boundaries, source identity, and unresolved contradictions.
- **Soft inherit:** prior models, heuristics, analogies, and preferences. Present them as optional hypotheses or comparison points.
- **Default exclude:** old final prose, unrelated Skills, stale project state, full transcripts, and concrete execution rules that do not constrain the current question.

Use one continuous main task for concept lineage. Use parallel agents only for independent breadth, bounded evidence collection, or disjoint verification; let the main task synthesize.

## Pass the crystallization gate

Before implementation or a real run, produce a compact crystallization packet:

```markdown
**Reasoning source:** task or artifact pointer
**Objective:** intended change or outcome
**Verified facts:** minimum evidence-bearing facts
**Settled decisions:** choices no longer under discussion
**Open design space:** choices left to the executor
**Assumptions to test:** falsifiable unknowns
**Protected boundaries:** non-goals and forbidden changes
**Acceptance evidence:** observable pass criteria
**Reopen when:** contradiction, invalidation, or missing authority
```

Keep exploratory prose with its native task. Persist only a durable decision, compact open question, or evidence pointer when the record admission test passes. Do not create a parallel knowledge database merely to copy the dialogue.

## Execute from the contract

- Resolve the active workflow and current authority before acting.
- Apply all rejection gates before the first governed mutation.
- Start with the smallest checkpoint that can disprove the chosen approach.
- For homogeneous broad work, run one baseline pass, freeze passed items, then repair only the failed subset once.
- Reopen a settled design choice only when its `Reopen when` condition occurs; return to the project lane before changing strategy.

## Reflect from effects, not activity

Separate four boundaries:

1. **Attempted:** the action or command started.
2. **Executed:** the tool or workflow reached its terminal signal.
3. **Effect verified:** the intended artifact, UI, account, or external state was directly observed.
4. **Accepted:** all stated evidence and recovery conditions passed.

Where evidence arrives asynchronously, wait only through a bounded read-only settlement window. A valid no-action or negative result records the evaluated scope, decisive gate, proof of non-mutation, and next legal condition.

After reflection, choose one action: reject transient narration, link to the native authority, update project truth, record a validated lesson, or propose a cross-project candidate. Never promote directly from an attractive idea or a single unresolved event.
